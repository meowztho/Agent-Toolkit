# Broad Reference Coverage Campaign

Read this for a broad authorized request to understand or extract a whole reference system. It is a routing method, not a fixed analysis pipeline or a second Reconstruction owner. The target supplies its own partitions and relevant evidence classes. Future product choices do not decide what reference information is worth collecting.

## Build a live coverage map

Start with the strongest available identity for every build, package, deployment, account or environment that can change observations. Enumerate known entry points and populations: applications and processes, pages and states, API routes and message types, stores and schemas, packages and resources, code modules, jobs, assets and variants. Keep a hierarchical map for a large target rather than truncating it to a convenient sample.

When a mission names multiple distinct products, keep a separate map for each and route extension/interoperability questions through `../../rore-reconstruction/references/MULTI_REFERENCE_EXTENSION_SEAMS.md`. A possible connection does not collapse their identities or make one product's evidence cover the other.

For each material partition record:

```text
reference identity / partition / known population or denominator
current Evidence, Findings, Paths and reference-native Models
level reached: present | referenced | reachable | exercised | effective | causal mechanism
coverage: unexamined | partial | covered | attempted/failed | blocked | not applicable
next discriminating observation + method/capability/provider
contradictions, provider limits, confidence and remaining unknowns
```

An inventory can establish a population but is not behavioral coverage. A sampled file, endpoint, screen or asset establishes only that sample. When the denominator is unknown, say so and keep discovery open. Use stable identities and cross-layer links to connect partitions without flattening their native architecture.

When a binary investigation reports rebuild or comparison progress, bind each count to the exact reference build, unit inventory and comparison method. Keep exact matches, heuristic similarity, untouched/copied bytes, untested units and unknown denominator portions distinct; changes to splits or inventory can change percentages without adding reference understanding. Comparison progress is one static evidence view, not the coverage or completion verdict for the whole reference.

## Follow leads across boundaries

Treat static strings, imports, exported symbols, UI labels, route lists, schemas and asset files as leads. For each material lead, ask whether it is referenced, reachable, exercised and effective. Obtain the next boundary through source/call/data flow, controlled inputs, UI actions, process and memory traces, storage differentials, packet/HTTP captures, or failure probes as appropriate. Work back from an observed effect to its producer and forward from an input to its state and outputs. A successful probe closes its question, not other technically accessible areas.

| Knowledge class | Candidate population | Stronger evidence to seek |
| --- | --- | --- |
| Surface and interaction | screens, DOM/view trees, controls, navigation, accessibility, media | state transitions, input/output traces, screenshots/video with starting state, timing and outcomes |
| API and protocol | routes, messages, schemas, auth/session flows, error codes | actual requests/responses, sequence/state rules, retries, boundary and failure cases; distinguish client projection from server behavior |
| Data and persistence | files, tables, formats, defaults, configuration, caches | create/edit/delete and recovery differentials, writer/reader paths, migrations, constraints and versioned semantics |
| Assets and resources | images, fonts, audio, models, shaders, localization, embedded blobs | raw bytes and native properties, variants and lineage, load/reference/reachability, actual presentation/use and missing resources |
| Architecture and internals | packages, processes, modules, functions, imports, jobs | responsibility and dependency paths, call/data flow, runtime boundaries, concurrency and failure recovery tied to the exact build |
| Runtime and network | processes, files, registry, storage, sockets, IPC, services | baseline-to-effect traces, traffic payloads and timing, counterpart identity, causal probes and cleanup/residue |

This table names evidence opportunities, not required tool stages. Reconstruct the reference's own unusual structure and conflicting layers; do not normalize it into a future design. Preserve full raw responses, assets and traces where allowed, with hashes and a navigable index. If a single bundle exceeds the CLI transport cap, keep companion raw archives or directories and their identity manifests; do not replace them with summaries or silently omit large media.

## Escalate instead of stopping at the first layer

If an accessible class is still at `present` or `candidate`, select the next evidence boundary. A missing GUI observer, decompiler, packet capture or parser triggers capability-first acquisition or a focused helper when tools were authorized; a named provider failure is not a reference unknown. If the target can be run or changed with a bounded baseline and verified recovery, perform the high-information probe. A VM, separate account or perfect isolation is not a blanket prerequisite; a file copy alone also does not cover registry, AppData, databases, network or child processes. Record the actual boundaries and instrumented differences.

For very large systems, iterate by subsystem, user flow, API group, state family or asset collection. Keep the population map and cross-partition links so local progress cannot masquerade as whole-system completion. Breadth discovers neglected areas; depth follows technically accessible internals and edge cases. Do not discard a reachable avenue merely because no later implementation decision has been made.

## Broad stop and handoff

Before a broad mission is called complete, review every applicable partition and knowledge class. Show acquired coverage, attempts that failed, feasible avenues not yet attempted, access or capability blockers, and facts that genuinely cannot currently be recovered or inferred. If material avenues remain accessible, continue or explicitly report a partial handoff with the next probe; do not relabel it replication-ready. Keep the raw evidence and index separate from revisable Findings, Paths, Models and narrative.
