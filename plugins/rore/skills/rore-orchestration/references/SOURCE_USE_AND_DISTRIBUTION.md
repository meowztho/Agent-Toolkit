# Source, Use and Distribution Boundaries

Treat these as separate decisions:

```text
access / observe / analyze / transform
!= retain locally
!= share / VCS / collaboration upload
!= include in another product
!= redistribute
```

RORE records the relevant boundary with the evidence when material. Technical visibility never implies redistribution permission. Keep raw or restricted artifacts local-only when required and preserve provenance for transformed/derived views.

## Action-level analysis scope

Derive scope from the user's actual request, supplied target, project context and earlier permissions in the session. A request to reverse-engineer or understand a named or unambiguously supplied reference authorizes a broad investigation of that reference to the requested depth unless the user sets a narrower boundary. Do not demand a separate declaration of ownership, legal justification or permission for every file, function or ordinary analysis step. The default covers reading and copying the supplied local artifact and its included components, extraction, hex inspection, decompilation, debugging/observation and analysis of its assets and behavior. It also covers bounded, reversible local probes of that target when baseline, effects and recovery can be established. A broad request is not limited to methods the inexperienced user happened to name.

Resolve `target identity + surface/account/environment + operation + expected side effects` internally before target-touching work. Record the scope source once for a campaign and update it only when a material boundary changes; this check is not an automatic question or approval gate. Normal execution of supplied local software may be used when its likely local and external effects are understood and bounded. Observing network traffic generated by that execution is within the target investigation; actively probing a newly discovered remote service is a separate target action. For a named public website or API, ordinary navigation and non-disruptive observation of its named surface are in scope; access to private accounts, state-changing calls and other hosts depends on the request and available credentials. Included files, child processes and resources can be followed as parts of the named target, while a discovered account, unrelated host, tenant, external service, privileged environment or another person's data does not inherit scope merely from discovery. A new irreversible/destructive action, unbounded external effect or sharing/redistribution of acquired material likewise needs its own basis.

If a material boundary is unresolved, continue useful in-scope acquisition and ask one concrete question only about the blocked action. Do not turn missing access into a claim that the reference fact is unknowable. Record the decision and scope source for material interventions. Analysis, local retention, sharing/VCS upload, inclusion in a new product and redistribution remain separate decisions.
