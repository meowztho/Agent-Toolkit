# On-demand provider provisioning

Read this only when a needed evidence capability is unavailable. A request to investigate the named reference covers acquiring a needed freely available provider into a contained user-scoped location unless the user restricted installation or downloads. Reuse existing qualified capabilities first. Ask only when paid licensing, administrator/system-wide changes, credentials, unusual cost or a material external effect is required and unresolved. Orchestration identifies the question and capability; Reconstruction qualifies the selected provider and records its acquisition. Provisioning does not become a fourth RORE owner, a fixed attack pipeline, or permission to analyze a new target.

1. Run `python scripts/rore_setup.py doctor` and check the current host/project tools. A PATH hit is only a candidate; inspect its exact version and operation before trusting it. Reuse a working capability when it answers the question.
2. Choose a provider by the missing evidence boundary, target format, host and authorization. Check its official distribution, license, version, architecture, dependencies, expected outputs and likely filesystem/process/network effects. Tool-master entries in `PROVIDER_SEEDS.md` are leads, never install commands.
3. When native loader-aware analysis on Windows x64 needs Ghidra, use the packaged [setup procedure](../../../docs/PROVIDER_SETUP.md): the `rore-providers` MCP can plan, start setup or start analysis with on-demand setup; the standard-library CLI offers the same setup without MCP. The recipe uses pinned official release ZIPs, checks size and SHA-256, extracts into a user-selected directory without changing system PATH or registry, then probes components. `probe` is not a target smoke test; run a known-answer operation and check actual target interpretation before promoting output.
4. For another provider or platform, research the **current official** binary/source and supported install method at execution time. Prefer a contained user-scoped install when practical. If using a package manager, verify the exact publisher/package ID and version before installation; do not execute a catalog example or pipe an uninspected remote script into a shell. Obtain an upstream checksum/signature where available, record the exact artifact and verify it. State any unavoidable privilege, license, network or target effects before the action. If one repository, release URL or provider is unavailable, return to `CAPABILITY_FIRST_TOOLING.md`: try a qualified alternative provider, existing capability or bounded helper. Record the failed acquisition; keep the reference question open until the required evidence boundary itself is unavailable.
5. After installation, record source URL/package ID, artifact digest or signature basis, installed path, version/build, host, dependencies, commands, outputs, errors and side effects. Exercise the exact requested operation on a representative known-answer input. Link raw output to Evidence; do not infer completeness or correctness from installation or `--version` alone.

Python 3.10+ is the minimal CLI prerequisite. The optional MCP additionally requires `uv` and access to the locked Python dependencies. On Windows, the official uv documentation provides `winget install --id=astral-sh.uv -e`; verify the publisher and current package identity before using it. If Python/uv is absent, acquire it from its official distribution through the host's normal package path, then rerun `doctor` and the package gate. RORE never installs a whole tool catalog or launches a target as part of plugin activation.
