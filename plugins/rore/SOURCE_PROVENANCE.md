# Source provenance

RORE v0.4.0 evolves from CoreReplica v0.3.6 and preserves its source-attribution lineage.

## Native-tool integration research (RORE v0.15.1)

The user-supplied `RORE – Ergänzende Recherche: Native Reverse-Engineering-Werkzeugintegration` prompted a comparison with existing RORE contracts. Ghidra's official `ReferenceManager`/`Reference` API informed an independently written extension of the existing RORE export script. Official GDB, LLDB, x64dbg and Frida interfaces informed conditional provider guidance; no third-party bridge, external tool code, debugger, decompiler or recompiler is copied or required. N64Recomp and XenonRecomp remain platform-specific methodological examples rather than an imported runtime or universal capability.

## CoreReplica v0.4.0 review (RORE v0.15.0)

The installed `corereplica-skills` v0.4.0 package and the earlier user-supplied `CoreReplica_v0.3.4_pre_rore.zip` were compared with RORE v0.14.0 after an independent integration report. CoreReplica's workspace classification, probe assumption map, retry/concurrency/parser/recovery questions and runtime claim boundary informed targeted additions to RORE's existing JIT references. RORE already covered the larger probe families, rights separation and independent reference Evidence Review; those owners were not duplicated. CoreReplica's downstream Product, Build and target Verification roles were not admitted.

`scripts/rore_imgdiff.py` is adapted from the MIT-licensed `corereplica-verify/scripts/imgdiff.py` in installed CoreReplica v0.4.0, copyright (c) 2026 CoreReplica contributors. `LICENSE-COREREPLICA` retains its MIT license. RORE changes its CLI and output from original-versus-clone parity to reference-capture difference discovery, removes the acceptance threshold/verdict, adds input digests and bounds PNG input size. The coarse edge-density indicator is not a semantic or functional equivalence measure.

## Optional installed Ghidra provider (v0.9.0)

The new `rore_runtime/ghidra_adapter.py` and `providers/ghidra/ROREExport.java` are RORE-owned code written for Ghidra's public headless script API; no Ghidra engine/source files are copied into the plugin. An external Ghidra 12.1.4 PUBLIC distribution and Eclipse Temurin JDK 25.0.4.1+1 were obtained separately on the test host and verified against their published SHA-256 values (`ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db` and `00c847d804f4a78e9f04f2683faf14fed898535b177b7fc704486cb0284e9283`). They are not package contents or runtime dependencies for other RORE operations. An actual Windows `where.exe` import/export/decompile run established this one-host provider path; it does not qualify every Ghidra version, target format or processor, and no independent semantic reconstruction was claimed. Ghidra 12.1.4 declares Java 21 as its minimum; JDK 25 was the tested choice.

RORE v0.10.0 pins those two official release artifacts in its own `provider_setup.py` Windows x64 recipe. The Ghidra and Adoptium GitHub release APIs identify the 569,649,598-byte and 141,167,264-byte archives and the SHA-256 values above; both local ZIPs were rehashed before an actual install test. The installer downloads or accepts those exact ZIP bytes, but the ZIPs, Ghidra runtime and JDK are not bundled in the plugin. Other provider guidance is an independently written, capability-first JIT method, not copied executable tool-master/REA catalog code or an assertion that every provider was tested.

RORE v0.16.0 adds a RORE-owned MCP transport and retained local jobs over that existing setup/analysis code. No provider runtime, third-party MCP bridge or upstream reverse-engineering implementation was copied. A real MCP setup call on an already installed Ghidra/JDK pair, a fresh setup from verified local release ZIPs into a new root, a combined absent-provider/automatic-install/copied-PE analysis job and paged decompilation call were exercised. These do not establish a live network download through MCP or completeness for arbitrary targets.

## Public decomp.dev and objdiff method review (v0.16.1)

The 2026-10-15 decomp.dev notice (`https://decomp.dev/`) and objdiff documentation (`https://github.com/encounter/objdiff`) were reviewed as public methodological sources. ## v0.4.0 architectural rewrite
The v0.4.0 rewrite is RORE-specific. It converts the earlier reference-recovery core into a reference-only plugin with three responsibilities: Orchestration, Reconstruction and read-only Evidence Review. It adds no downstream product compiler or replica implementation owner.
